# score.cpp —— 符卡栏位 512 运行期扩容（DLL 内）

## 是什么

把 th17.exe 的符卡数据栏位从 101 扩到 **512**，做法是**在当前进程内存里改 131 处常量**，
**不修改 th17.exe 文件**（所以会校验 exe 的 mod 不受影响）。

作为独立文件放在 DLL 工程里，和 `ins2xxx.cpp` / `intvar.cpp` / `binhack.cpp` 并列，方便单独管理：

```
ECLplus/
  score.cpp         实现：读开关 → 全量预检 → 打补丁 → 控制台/日志输出
  score.h           接口（InitSpellSlots），含编译期默认值 ECLPLUS_DEFAULT_SPELL_SLOTS
  score_table.h     131 条补丁表（自动生成，勿手改；来源 tools/gen_loader_table.py）
```

调用点：`ECLplus.cpp` 的 `init()` 里，跟在 `#ifdef DEV InitConsole();` 之后：

```cpp
VOID init() {
#ifdef DEV
    InitConsole();
#endif
    InitSpellSlots();       /* 符卡栏位 512 运行期扩容（见 score.cpp，开关在 ECLplus.ini） */
    InitBinhacks();
    ...
}
```

## 开关

| 方式 | 怎么写 | 说明 |
|---|---|---|
| `ECLplus.ini`（与 DLL 同目录） | `[ECLplus]`<br>`SpellSlots=512` | **推荐**，512=开 / 101=关，不用重编译 |
| `ECLplusLoader.ini`（同目录） | 同上 | 如果同时用启动器，可以共用一份配置 |
| 编译期 | `score.h` 里的 `ECLPLUS_DEFAULT_SPELL_SLOTS` | 1 = 512（默认），0 = 101 |

`ECLplus.ini` 还可加 `Force=1`（见下面「时序检查」）。

## 输出

- **控制台**：`Release-dev` / `Debug-dev` 自带控制台（项目里 `#ifdef DEV InitConsole()`），
  用 `WriteConsoleW` 输出，**中文不受代码页影响**：

```
[ECLplus/score] 符卡栏位模式：512 槽（开关来源：ECLplus.ini）
[ECLplus/score] 目标模块基址 0x00400000，共 131 处补丁待检查。
[ECLplus/score] 扩容补丁已应用：131/131 处。记录大小 0x18020，符卡数组起点（记录内）0x4820，
                尾块偏移 0xF0148，对象大小 0xF05F8
[ECLplus/score] 注意：512 槽写出的 scoreth17.dat 是扩容格式，与原版不通用；
                切回 101 槽前请先用存档工具把存档转回原版格式。
```
  关闭时只有：`符卡栏位模式：101 槽（开关来源：…）` + `原版 101 槽，未做任何内存修改。`
- **日志**：同目录 `ECLplusSpellSlots.log`（UTF-8）。非 DEV 版没有控制台，看这个文件即可。

## 安全机制

1. **全量预检**：131 处先全部读一遍；任何一处既不是旧值也不是新值 → **整批放弃、一处不写**，
   并打印第一处不符的地址（版本不对 / 已有别的补丁改过时会这样）。
2. **时序检查**：如果 `SCOREFILE_PTR`（0x4B77DC）已经非 0，说明存档对象已创建、布局已按旧值分配，
   这时再改常量会造成对象与代码不一致 → **本次不打补丁**并给出提示（想强行打可加 `Force=1`）。
3. 补丁表与 `th17.exe`（未修改版）逐条交叉核对；与 ECLplus 自身的补丁地址**无重叠**。

## 实测记录

| 测试 | 做法 | 结果 |
|---|---|---|
| 进程内补丁生效 | 挂起启动 th17.exe → 注入 → 读目标内存 | `0x4820 → 0x18020`、`0xe32943 → 0x2aa71d`、`0x903 → 0x3003`（131/131）✓ |
| 真实 ECLplus DLL（Release-dev） | 同上，注入 `ECLPLUS.dll` | 补丁生效、进程存活、ECLplus 其它功能不受影响；日志打印「512 槽 / 131 处已应用」✓ |
| 时序检查 | 挂起进程（`SCOREFILE_PTR=0`） | 判定为「足够早」，正常打补丁 ✓ |
| 预检 | 最小测试 DLL 打印 | 旧值 131 / 新值 0 / 不符 0 ✓ |
| 开关=101 | `ECLplus.ini` 写 101 | 一处未改，输出「原版 101 槽」✓ |
| 不符时拒绝 | 启动器版故意改坏一个字节 | 「有 1 处与预期不符，放弃打补丁」✓ |

## 注意

- **512 模式的存档与原版不通用**：512 模式写出的 `scoreth17.dat` 每条记录 `0x18020` 字节。
  切回 101 槽前，请先用 `th17_存档解密器.html` 把存档转回原版格式。
- 已知限制（与文件补丁版一致）：游戏自带菜单的符卡列表仍按 101 条显示；
  读档默认初始化也只填 0..100 号的 index/难度；101 号之后的符卡数据能正常读写与保存。
- 建议自己在 ini 里把开关切成 101 / 512 各跑一局对比确认。

# score_ui.cpp —— 战绩页符卡列表：自建表 + 自建渲染（v9）

## 是什么

战绩页（Player Data / 戦歴を表示）里的符卡列表，原本由游戏自己按 101 条固定表绘制。
本模块让你用一份 **spell_table.csv** 决定：

- 每一页（难度）显示哪几条、按什么顺序
- 每一条显示什么名字（可覆盖存档里的原名）
- 每一条读存档里的**哪个内部槽位号**（这个号只在表里用，不上屏）

并且**自己接管整段绘制**，每行输出：

```
No.组内序号  名字   M 取得/遭遇 収率   P 取得/遭遇 収率
```

- `M` = 主模式（通常游戏）；`P` = 练习模式（スペルプラクティス）
- 収率 = 取得 ÷ 遭遇，四舍五入到整数百分比；遭遇为 0 时显示 `--`
- 颜色沿用游戏规则：有数据且取得>0 → 亮黄(0xFFFF80)；只有遭遇 → 白(0xEFEFEF)；都没有 → 灰(0x808080)

## CSV 格式

```
分组,内部槽位,显示名
分组,显示名,内部槽位        ← 两种列序都支持，自动识别（名字在前、槽位放最后）
@PAGE_ROWS=10               ← 每页几条
@PAGES,N=2                  ← 该分组页数（只记录；页数上限目前仍由菜单逻辑决定）
# 注释
```

- 分组：`E / N / H / L / EX` 对应 5 个难度页；其它名字（如 `EX2`）会自动分配一个新编号（≥5），
  但**游戏菜单目前翻不到 ≥5 的页**，要新增难度页需要再改菜单的翻页逻辑（下一步）。
- 顺序 = 屏幕上从上到下的顺序；行号 = 组内序号（与内部槽位号无关）。
- 某分组一行都不写 → 该页**不接管**，保留游戏原有列表（安全兜底，已实现）。
- 名字留空 → 用存档里的原名。名字按字节原样交给游戏（游戏是 Shift-JIS 字体，
  建议用日文/半角；汉化补丁改过字体的话中文也能显示，实际以游戏内为准）。

## ini 开关（`[ECLplus]`）

| 键 | 默认 | 说明 |
|---|---|---|
| `SpellTable` | 0 | 模块总开关 |
| `SpellTableRender` | 0 | **自建渲染**（本版新增，要用就设 1） |
| `SpellTableInit` | 1 | 读档时把 index/难度 初始化到 512 项 |
| `SpellTableFilter` | 1 | 难度过滤表换成自建表 |
| `SpellTableLimit` | 1 | 把游戏自带上限放宽到表里最大槽位 |
| `SpellTableNames` | 1 | v7 只换名字的方案（`Render=1` 时自动跳过，避免重复画） |
| `SpellTablePos` | 0 | 0 = 用游戏自己的行 VM 坐标（对齐最准）；1 = 用固定坐标 |
| `SpellTableX` / `SpellTableY0` / `SpellTableDY` | 96 / 152 / 16 | 固定坐标：首行 X、首行 Y、行距 |
| `SpellTableXOff` / `SpellTableYOff` | 0 | 在算出来的坐标上加偏移（微调） |
| `SpellTableAlignH` / `SpellTableAlignV` | 0 / 1 | 对齐方式（0/1/2），战绩页文字左对齐用 0 |
| `SpellTableFont` / `SpellTableShadow` / `SpellTableDuration` | 2 / 1 / 1 | 字体号、阴影、每条文字存活帧数 |
| `SpellTableRowLog` | 1 | 头 3 帧把每行读到的数据写日志（排查用） |

## 每个字段是从存档哪儿读的（逆向结论，有 exe 代码为证）

记录基址 = `[0x4B77DC] + 槽位 × 记录大小`（512 模式 0x18020，原版 0x4820）；
符卡条目 = 记录基址 + 名字偏移 + 号 × 0x9C（名字偏移运行时读 `0x41AD90`：原版 0x8D8 / 512 模式 0x4828）。

| 偏移 | 含义 | 证据 |
|---|---|---|
| +0x00 | 名字（10 字节 Shift-JIS） | `0x41AD6A` 遭遇时把名字 strcpy 到这儿 |
| +0x80 / +0x84 | **取得回数 主 / 练习** | `0x41B249-0x41B274` 取得时自增；`0x41AC2D` 横幅 ≥100 显示 `MASTER` |
| +0x88 / +0x8C | **遭遇回数 主 / 练习** | `0x41ADEC-0x41AE03` 遭遇时自增 |
| +0x90 | index（符卡号） | `0x44FEDD` 读档初始化写入 |
| +0x94 | 难度（表 `0x4A0CA0` 的值） | `0x44FEE4` 读档初始化写入 |
| +0x98 | 分数 | `0x45C842` 战绩页 `SCORE %8d0` 读的就是它 |

> 注意两个基址差 8 字节：游戏绘制代码用的是 `[0x4B77DC] + 槽位×记录大小 + 0x958` 这种写法
> （= 名字偏移 − 8 + 0x80），上面表格已经换算成"从名字偏移算"的干净形式。

## 文字位置 API（本次逆向确认）

`AsciiManager::create_string` **0x408190**，`__thiscall`：

```
ecx = [0x4B7678] ASCII_MANAGER_PTR
参数: (const zFloat3* pos, const char* text)   ret 8
```

它把 `pos`（3 个 float，640×480 虚拟坐标）和 AsciiManager 的"当前状态"
（color +0x19214、scale +0x19218、font_id +0x1922C、draw_shadows +0x19228、
render_group +0x19230、duration +0x19234、align_h +0x19238、align_v +0x1923C）
拷进新条目 `ascii + 0xC10 + n*0x138`（n = +0x19210，上限 0x140）。

本模块用它画每一行：坐标优先取游戏自己的行 VM 位置
（`[菜单+0x74C+行*4]` → `AnmManager::get_vm_with_id`（0x476470，`ret 4`）→ `vm+0x2C` 的 zFloat3），
拿不到 VM 就用固定坐标；每一帧先用 `zAsciiStr +0x118` 上的标记清掉自己上一帧写的条目，
所以永远不会出现重影/叠加。

## 为什么"不显示"（v9.2 诊断结论）

`0x4587F0`（符卡列表绘制）**只在这道门成立时才会被调用**：

```
00457e52  mov eax,[菜单+0x20]              ; 战绩页的子页号 0..3
00457e5e  jmp [eax*4 + 0x4587E0]           ; 4 条目跳转表 → 457E65 / 45814C / 45816E / 4587A0
00457e65  (子页 0) mov eax,[菜单+0x24]      ; 该页里的"模式/选择"
00457e6b  mov [菜单+0x5DF0], eax           ; 存成模式快照
00457e77  cmp eax,1 / jne 跳过             ; 只有 ==1 才进符卡列表这条路
...
00457fc9 / 0045824a / 0045831d / 00458349  call 0x4587F0   ; 4 处调用，前面都判断 +0x5DF0==1
```

也就是说：战绩页里"**最高分记录**"和"**符卡数据表**"是同一个子页的两种**模式**，
只有切到模式 1 才走符卡列表那条绘制。没切到那个模式时，接管函数一次都不会被调用
（日志里没有 `[T1]`、也没有崩溃——与现象完全一致）。

v9.2 加了两样诊断，跑一次就能定位：

| 开关 | 作用 |
|---|---|
| `SpellTableProbe=1` | 在 4 个 `call 0x4587F0` 调用点装**只记日志不改行为**的探针 → `[probe] 调用点#n（地址）：菜单 +20=… +24=… +5DF0=…` |
| `SpellTableStateLog=1` | 每 20 帧记一次菜单状态 → `[state] 帧=… 子页=… 选择=… 模式5DF0=… 难度FC=… 页1D4=… 钩子=在/已被覆盖` |

其中 `钩子=已被覆盖` 用来判断 thcrap 的 mod 是否在我之后又改写了 0x4587F0（它做字符串替换时会 patch 代码）。

## 实测记录

| 测试 | 做法 | 结果 |
|---|---|---|
| 探针安装 | 挂起启动 → 注入 → 读目标内存 | 4 个调用点全变 `E9 …`（跳板）、绘制入口 `55 e9 …`、日志「探针 4/4」✓ |
| 补丁安装 | 挂起启动 th17.exe → 注入新 DLL → 读目标内存 | `0x4587F0: 55 e9 …`（push ebp + jmp 到 DLL 接管函数）；过滤表 2/2、上限 2/2、读档表 1/2+跳板 1/2 ✓ |
| **钩子栈纪律** | `tools/uitest`（把真实 score_ui.cpp 包进测试程序，伪造 `push ebp` + jmp 的被打补丁入口，两条路各跑一次） | 两条路都 `esp 前后一致`、`ebp` 正确还原、返回值正确 ✓（**这就是下面那次崩溃的根因**） |
| 字段读法 | 用同一套公式在 py32 里读真实存档 | 槽位 6 的 108 号：练习 取得1/遭遇2 = 50%，与游戏自己写进去的一致 ✓（`tools/what_ui_will_show.py`） |

## 崩溃记录与修复（v9.1）

第一次交给用户测试时**游戏崩溃**（WER：th17.exe，0xC0000005，故障模块 unknown + StackHash）。原因：

- 这个绘制函数的**真入口是 0x4587F0**，第一条指令是 `push ebp`（0x55）；紧跟着 0x4587F1 才是
  `mov ebp,esp / sub esp,0xF4`（8 字节）。补丁覆盖的是后面这 8 字节。
- 也就是说进钩子时 `push ebp` **已经执行过**，而我"自己画完直接 return"那条路**没有把 ebp 弹掉**
  → 栈比调用者预期多 4 字节 → 调用者的 `ret` 跳到垃圾地址 → 崩。

修复（v9.1）：

1. handled 路径返回前补 `pop ebp`；fallback 路径保持"补回 mov ebp,esp / sub esp,0xF4 再跳 0x4587F9"。
2. 进自己的 C++ 代码前 `and esp,-16`（游戏栈不保证 16 字节对齐，SSE 代码可能因此 #GP），调用完恢复。
3. 渲染/日志路径**完全不再调用 CRT 的 `_snprintf_s`/`_vsnprintf_s`**，改用自带的 MiniFmt。
4. 整段渲染套 `__try/__except`：万一再出异常只写一行 `[crash-ui]`，本帧交回游戏自己画，**不把游戏带崩**。
5. 分步日志 `[T1]…[T5]`：下次真出问题能一眼看出死在哪一步。
6. 崩溃报告（`SpellTableCrashLog=1`）：VEH + 未处理异常过滤器，把 `异常码/地址/EIP(模块+偏移)` 写进日志。
7. 安装前校验 `0x4587F0 == 0x55`，不符就**拒绝接管**（宁可没有新列表，也不冒崩的风险）。

## 已知限制 / 下一步

1. **自定义分组（EX2 等）目前翻不到**：菜单的页数上限还是按游戏自己的 101 表算的，
   要真正"新增一个难度页"得改菜单的翻页枚举（`0x456FEC / 0x4570FF / 0x457155` 一带）——这是下一步。
2. **名字编码**：CSV 原样喂给游戏。游戏字体是 Shift-JIS 位图字体，中文可能显示不出来。
3. 位置/字号/行距先用 `SpellTableX/Y0/DY/XOff/YOff/AlignH/AlignV` 微调；
   如果一整块都偏了，多半是虚拟分辨率缩放（全局缩放 `[0x524718]`），改 XOff/YOff 即可。
4. 只想换名字、不想接管绘制：把 `SpellTableRender=0` + `SpellTableNames=1`（v7 老方案）。

## v9.3：不依赖游戏钩子的监控线程 + 延迟重装

你那次日志里，**6 个钩子（含"每帧必跑"的主菜单 tick）一个都没触发**，但 init 时每一个都通过了原版字节校验 →
说明我的补丁在 init 之后被"后来者"覆盖了。TH17 的界面文字是**以内联立即数写在代码里**的，
汉化包（thcrap）要翻译就得改那一片代码 —— 512 槽补丁改的是存档数据区、不在它范围内，所以一直有效。

这一版改成不依赖任何游戏钩子：

| 机制 | 说明 |
|---|---|
| 监控线程 | init 时 `CreateThread`，前 3 秒每 100ms、之后每 500ms 检查 7 个补丁点的首字节；一发现被改掉就记录**时间和替换后的 8 个字节** |
| 延迟重装 | `SpellTableReinstallMs=3000`：启动 3 秒后（thcrap 打完补丁）**再装一遍**；只在该处仍是**原版字节**时才写，若已被写成别的代码就记日志并跳过（不硬刚、不冒崩溃风险） |
| 持续补装 | `SpellTableRepair=1`：之后每次发现被覆盖就继续补装 |
| 菜单状态心跳 | 线程每 2 秒直接读菜单对象记一行 `子页/选择/模式5DF0/难度/页/槽`，**不依赖钩子**，所以即使钩子全掉也能看到你在哪一项、门（5DF0==1）有没有满足 |

顺手修掉一个自己的真 bug：自写的 MiniFmt 里补零循环没有推进计数，会把缓冲区填满
（`%#08X` 输出 1000 多个 0）→ 即使钩子生效，行文字也会是垃圾。已用独立测试 `tools/uitest/fmttest.c` 验证修好。

# v10 方案：自绘覆盖层（thprac 式，不依赖游戏字体）

## 为什么换路线

v9 一直"画不出来"，最后一版日志证明：渲染函数每帧都在跑（`[frame] 模式5DF0=1`）、没有崩溃，
但文字始终没上屏 —— 借游戏自己的 `AsciiManager` 渲染这条路，被两头夹死：
1. thcrap 用 **断点 + codecave** 改写"压入字符串"的指令（`base_tsa\th17\stringlocs.v1.00b.js` 里
   `Rxa2934 = "th15 Result Known Spell"` 就是符卡列表行格式 0x4A2934），任何改这块代码的补丁都会被它覆盖/冲突；
2. 接管整段绘制（跳过原函数）会让每行 VM 的文字没被初始化 → `AnmManager::draw_vm` 崩溃（实测 EIP 0x46CCE1）。

用户决定：**照 thprac 的做法，自己劫持、自己画**；底色用**不透明黑底**。

## 已验证可行的三个前提

| 前提 | 证据 |
|---|---|
| 每帧回调 | ECLplus 自己的 D3D9 EndScene 钩子在用户环境每帧都在跑（日志 `[frame] 帧=720/840/…`） |

## 重要内部机制（供以后继续开发）

- **游戏读的表已被解耦**：`PatchInitDiffTable` / 列表过滤表都指向内部 `g_emptyDiff`(全 0xFF)
  → 游戏永远不画符卡行；我们的表读 `spell_table.csv`（UTF-8，必须保持 UTF-8）。
- **页面判定**：探针 `call绘制#1..#4`(0x457FC9/0x45824A/0x45831D/0x458349) 命中置 `g_listDrawSeen`，
  再要求 `模式5DF0==1`；`SpellTableHideGameRows=1` 时不再要求行 VM。
- **行数据 API**：`SpellTableFormatRowCols`(跟随游戏) / `SpellTableFormatRowAt(group, idx, ...)`(自控)；
  `SpellTableGroupLabel` 用 `g_groupTag[]` 显示 CSV 真实分组名。
- **自机维度**：尚未做。方案：探针记录菜单字段→用户左右切自机→找出自机编号字段→
  `组 = 自机 × 每组数 + 难度`。CSV 侧也可先用前缀分组名（如 `灵梦-N`）配合 `GuiOwnView=1` 的标签。
- **退出动画**：展开 5 帧"一条线上下展开"，内部切换不重播，退出 1 帧直接消失（游戏缩小动画字段始终没定位到）。
- **已知坑**：不要用 3 参数的 `String.Replace`；改动前先用锚点+写后复核（本次多次因静默替换失败浪费时间）。
